# 简历预览性能基线与优化记录

本文档记录简历预览与编辑链路的性能基线、采集方式与每次优化的复测结果。
基线由 `apps/web/scripts/perf-baseline.cjs` 采集，优化前后必须用同一脚本、同一机器复测。

## 采集方式

```bash
pnpm dev:web                                   # 本地起 dev server（默认 5174）
pnpm --filter @snowflake/web perf:baseline     # 采集并打印 JSON，可追加输出路径
```

脚本用真实 Edge + CDP 跑两条链路：

- **A 模板页**：进入页面到首屏可用（`bootMs`）→ 切到样式分类到卡片渲染完成（`styleRenderMs`）→ 滚动揭示全部样式卡片后的整页规模与主线程增量。
- **B 编辑器打字**：用第一张内容范本进入编辑器，聚焦正文富文本编辑器，连发 24 组按键事件（每组插入 2 个字符），记录主线程增量与测量树 DOM 变更次数。`typedDelta` 用于确认按键真的落进了编辑器，为 0 说明这次采集无效。

主线程增量取 `Performance.getMetrics` 的差值：`Layout`、`RecalcStyle`、`Script`、`Task`（单位毫秒）。

## 初始基线（优化前）

环境：Windows + Edge headless（`--headless=new`，1600×1000，deviceScaleFactor 1），dev server 5174，2026-10-02。

| 指标            | 模板页                                 | 编辑器打字（24 组按键 / 48 字符） |
| --------------- | -------------------------------------- | --------------------------------- |
| 首屏            | `bootMs` 899ms，`styleRenderMs` 2178ms | 进编辑器后 DOM 5401 节点          |
| DOM 规模        | 22144 节点（27 张卡片），测量节点 693  | 5521 节点，测量节点 26            |
| Layout          | 254 次 / 260ms                         | 192 次 / 50ms                     |
| RecalcStyle     | 1013 次 / 250ms                        | 294 次 / 50ms                     |
| Script          | 90ms                                   | 30ms                              |
| Task 合计       | 4970ms                                 | 1140ms（约 **47ms / 组按键**）    |
| 测量树 DOM 变更 | —                                      | 6552 次（约 273 次 / 组按键）     |

## 观察到的热点

1. **打字期间测量树整体重渲染**：26 个测量节点的树，每组按键产生约 273 次 DOM 变更，远超节点数；测量与 Vue 渲染叠加后每组按键约 47ms 主线程时间，是打字卡顿的主要来源。
2. **模板页整页渲染 27 张卡片**：22144 个 DOM 节点、693 个测量节点、约 5s 主线程任务时间；卡片是整页 `ResumePages`（含隐藏测量树），一次性全量挂载。
3. 编辑器 DOM 有 5401 个节点，其中测量树只有 26 个，主要是表单侧面板占用量。

## 打字开销拆分（`--trace` + `--profile`）

```bash
pnpm --filter @snowflake/web perf:baseline -- --trace     # 主线程子阶段
pnpm --filter @snowflake/web perf:baseline -- --profile   # CPU 采样热点
```

24 组按键（每组 2 个字符）的主线程约 1660ms，约 47ms / 组。trace 子阶段：

| 子阶段           | 次数 | 合计   |
| ---------------- | ---- | ------ |
| Layout           | 143  | 84.1ms |
| Layerize         | 114  | 57.8ms |
| Paint            | 512  | 45.8ms |
| UpdateLayoutTree | 242  | 39.1ms |
| PrePaint         | 116  | 30.8ms |
| FunctionCall     | 2732 | 63.9ms |
| TimerFire        | 98   | 21.1ms |
| ParseHTML        | 4182 | 12.8ms |

CPU 采样自身耗时 Top：`traverse` **178.9ms**、`get` 85.9ms、GC 78.8ms、`patchDOMProp` 70.4ms、`update` 64.2ms、`appendChild` 59.9ms、`setStyle` 42ms、`setFullProps` 29.7ms。

结论：打字开销约一半在 JS（每组合计约 24ms），其中 `traverse` 一项约占 7.5ms / 组；另一半在样式重算、布局与绘制（约 11ms / 组）。

## 生产构建复测（关键结论：dev 数据不能直接当优化依据）

```bash
pnpm --filter @snowflake/web build
pnpm --filter @snowflake/web preview
pnpm --filter @snowflake/web perf:baseline -- --profile --trace --url=http://localhost:4173 --hash
```

生产构建用 hash 路由，`--hash` 才能直接打开路由；`--spa` 用于资源为相对路径的场景。

同一台机器、同一次流程（24 组按键 / 48 字符）：

| 指标                             | dev server    | 生产构建     |
| -------------------------------- | ------------- | ------------ |
| 主线程 TaskDuration              | 1660ms        | 1570ms       |
| `traverse`（Vue 深监听遍历）     | 178.9ms       | 未进入热点榜 |
| `createHTML`（HTML 解析/序列化） | 未进入热点榜  | 306.8ms      |
| `vue-draggable` 相关             | 未进入热点榜  | 199.5ms      |
| Layout / UpdateLayoutTree        | 84.1 / 39.1ms | 100 / 40ms   |
| 模板页 TaskDuration              | 4970ms        | 4600ms       |

结论：dev 下最热的 `traverse` 是 Vite dev + Vue DevTools 带来的开发期开销，生产环境并不存在；生产环境打字的真实大头是富文本的 HTML 解析（`createHTML`）与表单拖拽库（`vue-draggable`）的响应式开销。**优化必须以生产构建的复测为准。**

## 度量方法（重要）

单轮 taskMs 波动很大：同一份生产构建、同一流程连跑三轮得到 **1000 / 1240 / 1590ms**，单次结果无法支撑优化前后的比较。因此基线脚本默认跑三轮取中位数，并同时输出每轮原始值：

```bash
pnpm --filter @snowflake/web perf:baseline -- --url=http://localhost:4173 --hash --repeat=3
```

优化前后必须用中位数比较，并同时记录每轮明细与确定性指标（DOM 变更数、实例数等）。`--inject-file=<路径>` 可在打字前注入一段脚本，用于 A/B 对照。

## 打字开销归属（A/B 对照）

在打字前隐藏预览页容器（测量树 Teleport 在 body 上，仍然照常测量），对比同一流程：

| 项目                        | 预览可见  | 预览隐藏 |
| --------------------------- | --------- | -------- |
| taskMs                      | 1270ms    | 1320ms   |
| `(program)` 非 JS 主线程    | 452ms     | 449ms    |
| 面板 DOM 变更 / 24 组按键   | 114       | —        |
| 测量树 DOM 变更 / 24 组按键 | 1273–1896 | —        |

结论：**预览不是打字开销的瓶颈**，隐藏它几乎不改变主线程耗时；DOM 变更也几乎都落在测量树（每 24 组按键 1273–1896 次），表单面板只有约 114–132 次。

## 字节字段类型对照（富文本 vs 纯文本）

用 `--focus=` 指定打字目标，其余流程完全一致，各跑三轮取中位数：

| 打字目标                            | 三轮 taskMs        | 中位数 | 测量树 DOM 变更 | 面板 DOM 变更 |
| ----------------------------------- | ------------------ | ------ | --------------- | ------------- |
| 富文本编辑区（`[contenteditable]`） | 1000 / 1240 / 1590 | 1240ms | 1273–1896       | 114–132       |
| 纯文本输入框（`input`，姓名等）     | 760 / 690 / 720    | 720ms  | 816（三轮一致） | 96            |

结论：**富文本字段比纯文本字段每组按键贵约 42%**（1240ms vs 720ms，差 520ms），而且它的测量树 DOM 变更量随内容增长而上升（纯文本三轮稳定在 816，富文本从 1273 涨到 1896）。原因是富文本节点用 `v-html` 渲染切片后的 HTML：每次按键都会重设 `innerHTML`，整块子树被重建并重新解析，这与先前观测到的 `createHTML` 峰值（267–307ms）是同一件事。下一步应针对这条渲染路径（例如按块渲染、只更新变化的文本节点），而不是继续在测量调度或面板上找收益。

## 优化方向（按生产复测收益排序）

1. **富文本渲染路径**：富文本字段比纯文本字段贵约 42%（中位数 1240ms vs 720ms）。节点用 `v-html` 渲染切片 HTML，每次按键重设 `innerHTML` 导致整块子树重建与重新解析（对应 `createHTML` 峰值 267–307ms）。可行方向：按块渲染富文本（解析器已经给出每个块的偏移区间，可按块切片，未变化的块保持节点标识）、或只更新发生变化的文本节点。
2. **表单拖拽实例**：已改为按下把手时才创建（编辑期不再常驻 Sortable 实例），机制与拖拽回归均已验证。
3. **渲染侧开销**：生产环境 `Layout` 约 60–100ms，`Layerize` + `Paint` + `PrePaint` 约 130ms，`(program)` 非 JS 主线程约 450ms。测量管线已经做了同帧合并（`useLayoutMeasurements` 有 `frameHandle` + `dirtyAt`/`measuredAt` 去重），节点对象也已按内容签名复用（`buildLayoutNodes` 的 `reuseUnchangedNodes`），所以这一项不是调度或重渲染范围问题，而是「重设 innerHTML + 强制布局」本身的规模问题。
4. **模板页整页渲染**：生产环境 4600ms TaskDuration、22151 个 DOM 节点、693 个测量节点；卡片缩略图必须依赖测量树，收益不明确，暂缓。

## 富文本按块渲染的可行性（已量化，本轮不改）

在编辑器里对真实富文本内容做微基准（内容 1820 个元素、58 个顶层块，各跑 20 次「追加一个字符并更新」）：

| 策略                         | 20 次耗时 | 折算单次 |
| ---------------------------- | --------- | -------- |
| 现状：整段切片 HTML 重设一次 | 63.5ms    | 3.2ms    |
| 按块渲染：只重设变化的那一块 | 1.1ms     | 0.055ms  |

按块渲染能把这一步的耗时降约 98%。但折算到真实打字：3.2ms × 24 组 ≈ 77ms，只占富文本比纯文本多出的 520ms 里的一小部分 —— 差额的大头在富文本编辑器自身与重建节点的布局、GC。按块渲染还要动引擎的切片口径（分页敏感），性价比不足，因此**只记录结论、本轮不改**，留作后续可选优化。

## 已排除的方向（避免重复投入）

| 方向                                                                            | 排除方式                     | 结论                                                                      |
| ------------------------------------------------------------------------------- | ---------------------------- | ------------------------------------------------------------------------- |
| `stores/modules/resume` 里的整份简历 `deep` 监听（dev 热点 `traverse` 178.9ms） | 生产构建复测                 | 开发期开销（Vite dev + Vue DevTools），生产不存在；改动它不改善用户体验   |
| `containerArray` 的拖拽列表响应式依赖                                           | 换成静态数组重建复测         | 开销不变，问题不在响应式依赖，而在 Sortable 实例的 DOM 观察               |
| 测量调度重复触发                                                                | 阅读 `useLayoutMeasurements` | 已有 `frameHandle` 同帧合并与 `dirtyAt`/`measuredAt` 去重，无重复测量     |
| 测量树整棵重渲染（节点对象身份）                                                | 阅读 `buildLayoutNodes`      | 已有 `reuseUnchangedNodes` 按内容签名复用节点对象，未被改动的节点不重渲染 |
| 预览页渲染量                                                                    | 隐藏预览容器 A/B             | 隐藏后 taskMs 与 `(program)` 基本不变，预览不是瓶颈                       |
