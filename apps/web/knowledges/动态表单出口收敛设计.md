# 动态表单出口收敛设计

状态：出口 A、B 已实施（`api.ts` 能力入口 + `useFormContext()` 类型化契约），出口 C 待排期。

## 背景

动态表单引擎（`src/components/business/dynamicForm`）近期陆续补入结构排序、字段增删、记录移动等能力，对外出口从最初的"一个 context"扩散成四条通道，且出口清单与真实依赖严重错位。本文记录现状诊断与收敛方案。

## 二、问题

### 1. 出口清单既不完整也不收敛

**根出口里 10 个函数外部零引用**，属于实现细节却当成契约暴露：

- orderData：`applyVisibleOrder`、`keepFixedFirst`（渲染层拖拽的实现细节）
- arrayData：`getArrayRecords`（容器内部读取）
- fieldData：`hasFieldData`、`addFieldData`、`removeFieldData`、`getFieldDataKey`（`dynamicForm.vue` / `createAddItem` 内部）
- schemaAccess：`getPrimaryModelBinding`
- schemaData：`resolveDefaultValue`、`createArrayItemData`

**反过来，用得最广的一组能力压根不在出口里**：`fieldVisible` 的 `isFieldHidden` / `isFieldRemoved` / `setFieldCheckValue` 被 5 处外部引用，只能全部走深路径。

**同一个能力存在两种取法**：`walkFormFields` 在 `useProgress.ts` / `useMarkdownExport.ts` 走根出口，在 `stores/modules/resume/index.ts` 走深路径；`getFieldLabel` 与 `createDataPathContext` 则一律走深路径，即使它们已在根出口中。

### 2. `export *` 让实现细节变成契约

`applyVisibleOrder` / `keepFixedFirst` 是渲染层内部实现，已经进入根出口。没有 `@internal` 标记、没有 lint 约束，契约面等于实现面，后续收不回来。

### 3. `df/context` 是无类型的字符串出口

- `inject("df/context")()` 返回 `any`，能力名靠记忆
- 改名、删除能力没有编译期保护
- 已经外溢到测试：`more.spec.ts` 手工 mock 字符串 `"df/context"`
- `currentLength` / `removeCurrent` 在非数组上下文是 `undefined`，这个"按上下文可选"的语义没有体现在契约里

### 4. 隐式出口

`"df-select-module"` 字符串在 `useModuleNav.ts`（2 处）与 `dynamicForm.vue`（2 处）硬编码，无常量、无类型。

## 三、设计：一个契约 + 两条具名出口

### 契约（收进 `types.ts`）

```ts
export interface FormContext {
  currentForm: Ref<FormField | undefined>;
  currentType?: "object" | "array" | "container";
  /** 仅数组容器提供 */
  currentLength?: Ref<number>;
  /** 仅被容器绑定目标的节点提供 */
  removeCurrent?: () => void;
  addItem: () => number | undefined;
  hasFieldData: (field: FormField) => boolean;
  addField: (field: FormField) => boolean;
  removeField: (field: FormField) => void;
  getFieldDataKey: (field: FormField) => string;
}
```

可选成员显式标注，把"按上下文可选"从隐式约定变成类型约束。

### 出口 A · 组件树内：`useFormContext()`

- `DF_CONTEXT` 由字符串改为 `InjectionKey<FormContext>`
- 新增 `useFormContext(): FormContext`，内部 `inject` + 缺失时明确报错
- 6 个业务组件改为 `const { removeCurrent } = useFormContext();`
- `more.spec.ts` 改为按 key provide

收益：类型安全、IDE 补全、改名可追踪。

### 出口 B · 组件树外：拆成组件入口与能力入口

**前置约束（实施时发现）**：`index.ts` 默认导出的是组件，而 `unplugin-vue-components` 正是按 `business/*/index.ts` 解析 `SfDynamicForm`，所以 `index.ts` 必须 `import DynamicForm from "./dynamicForm.vue"`。一旦把纯能力也从 `index.ts` 导出，任何引用纯函数的文件（store、hooks、测试）都会被拖进组件的依赖图，element-plus 的 `.css` 在 vitest 的 node 环境下直接报 `Unknown file extension ".css"`，实测会让 store 与 AI 相关的 9 个测试文件连带失败。

因此出口必须拆成两个文件：

| 入口                   | 内容                            | 使用者                                              |
| ---------------------- | ------------------------------- | --------------------------------------------------- |
| `dynamicForm/index.ts` | 仅默认导出组件                  | `unplugin-vue-components` 解析器、`<SfDynamicForm>` |
| `dynamicForm/api.ts`   | 契约类型 + 公共能力，零组件依赖 | store、hooks、编辑器面板、测试                      |

`api.ts` 的具体内容：

- 撤下 10 个零外部引用函数（内部继续使用）
- 补上 `fieldVisible` 三件套（当前最大缺口）
- 9 个深路径文件与非组件场景一律改从 `api` 导入
- `code/*` 回归为内部实现，可加 ESLint `no-restricted-imports` 约束

### 出口 C · 能力收敛（可选，单独排期）

- `stores/modules/resume/index.ts` 的 `findModuleArrayField` + `addArrayRecord` / `removeArrayRecord` / `moveArrayRecord` 三件套，本质是引擎该提供的"按模块定位数组字段并操作记录"，应下沉为语义 API
- `df-select-module` 抽常量

## 五、落地顺序与验收

1. 出口 B：拆组件入口与能力入口 + 消费方统一改从 `api` 导入（零行为变更）
2. 出口 A：`FormContext` 契约 + `useFormContext()` + 消费方与 spec 改造
3. 出口 C：能力收敛与事件常量化（单独排期）

验收标准：

- `api.ts` 的导出清单与外部引用清单一致，无冗余、无缺口
- 非组件场景不再从 `dynamicForm` 根入口导入任何运行时值（否则会拉入组件依赖）
- 业务组件中不再出现 `inject("df/context")` 字符串
- `grep -r "dynamicForm/code" src` 的结果只剩引擎内部文件

## 六、风险

- **出口必须与组件解耦**：`index.ts` 一旦承载纯能力，就会把 element-plus 与样式带进 store 与测试；这是"两个入口"设计的根本原因，后续不要在 `index.ts` 里追加任何运行时能力
- `DF_CONTEXT` 由字符串换 Symbol 属于破坏性变更，但提供方只有 `dynamicForm.vue` 一处，消费方 6 个组件 + 1 个 spec，影响可控
- 其余为导入路径调整，无运行时行为变化
- 撤下的 10 个函数已通过检索确认无外部引用
- 既有失败（与本设计无关，改动前后一致）：`stores/modules/resume/index.spec.ts`、`more.spec.ts`、`assistant/chat/emptyState/index.spec.ts`，原因同为 vitest 的 node 环境不处理 element-plus 的 `.css`
